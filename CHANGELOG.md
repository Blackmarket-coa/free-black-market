### Added
- **Asset-graph module (v0/v0.1)** — declarative intake layer that turns "writing a new vertical" into "writing a manifest." Six reference manifests cover every value in all four manifest-schema enums (`Lifecycle`, `SettlementRail`, `GovernanceModel`, `Surface`): yard-scrap-nursery (commerce/grove/individual), tool-library (threshold/commons/collective), repair-cafe (threshold/workshop/consensus), childcare-coop (threshold/commons/consensus, match-only sensitivity), creator-bounty-pool (refrain/atelier/vote-weighted, exercises the `capital` asset category), and courier-collective (blackstar/workshop/collective, depth-2 wildcard via `tool.vehicle.*`). End-to-end flow: member declares assets → matcher proposes manifests → operator accepts → ProjectInstance emits SettlementRecords → cross-module reconciler writes hawala-ledger entries (CCR/USDC/USD/HRS), karma_event rows (KARMA), or audit-only marks (GIFT). See `docs/ASSET_GRAPH.md` and `docs/manifests/`.
- 7 DB tables: `asset_kind`, `asset_declaration`, `attestation`, `project_manifest`, `project_instance`, `match_proposal`, `settlement_record` (the last with a partial-unique `idempotency_key` for systematic emitters). Catalog seeder at `backend/src/scripts/seed-asset-graph.ts` upserts both `asset_kind` and `project_manifest` from the in-code source of truth.
- Matching engine (`backend/src/modules/asset-graph/matcher.ts`): pure-function `evaluateConstraints` (`_min` / `_max` / exact-match vocabulary), `matchSlot` (wildcard + lifecycle filter + revoked-skip), `matchManifest` (per-slot reports + candidate operators), `proposalsFromReport` (one `MatchProposal` per candidate operator, 0/1 completeness score). Service surface: `runMatchManifest` (dry-run, in-memory) and `proposeMatches({ persist? })` (DB-backed, opt-in write).
- Instance lifecycle (`instance-lifecycle.ts`): two pure state machines (`transitionProposalState`, `transitionInstanceState`) plus `computeInstancePayload`. Service: `acceptProposal`, `declineProposal`, `publishInstance`, `pauseInstance`, `reactivateInstance`, `archiveInstance`. `InvalidTransitionError` carries `from`/`action` for context-appropriate UI messages.
- Settlement emission (`settlement.ts`): `composeSettlement` validates rail-against-manifest + per-rail required fields (CCR purchase context, HRS time-bank reference, KARMA reason, USD/USDC positive amount, GIFT audit-only). Service: `emitSettlementRecord` writes the row with `ledger_entry_id: null`; honors caller-supplied `idempotency_key` to dedup duplicate emits.
- Cross-module settlement reconciler at `backend/src/modules/asset-graph/reconciler.ts` + scheduled job `backend/src/jobs/asset-graph-settlement-reconciler.ts` (every 15 minutes). Per-rail dispatch: CCR/USDC/USD/HRS → `hawala-ledger.createTransfer`, KARMA → `createKarmaEvents`, GIFT → metadata stamp. `createTransfer` invoked with `idempotency_key=settlement-${record.id}` so re-runs return the existing entry; KARMA paths skip when a source-id match already exists.
- W3C Verifiable Credential payload validation at `attestations/vc.ts`: zod schema accepts both v1 and v2 contexts, exposes `getIssuerId`/`getCredentialSubjects`/`getValidityWindow`/`isCurrentlyValid`/`looksLikeVCPayload` helpers, and a `VerifiableCredentialError`. Service: `createAttestationWithVC` validates `external.vc_payload` at write time; legacy non-VC `external` blobs bypass via the heuristic gate. Cluster-3 childcare manifest's `credential.cpr-certified` / `credential.background-check` declarations now carry real VCs structurally.
- Member-side service methods: `createDeclarationFor` (validates attributes against the kind's zod schema in strict mode; defaults lifecycle and sensitivity-tier from the kind) and `revokeDeclaration` (ownership-checked; returns null on cross-member access — doesn't leak existence).
- Hawala-ledger rails registry at `backend/src/modules/hawala-ledger/rails.ts` — single source of truth for all six rails (CCR/USDC/USD/KARMA/HRS/GIFT) with per-rail `cash_convertible` / `closed_loop` / `requires_purchase_context` / `account_type` / `unit` properties. `RAIL_CODE_BY_MANIFEST_RAIL` translates between the asset-graph manifest enum and the ledger codes.
- Hawala-ledger HRS time-bank rail: new `TIME_BANK` `account_type` on `ledger_account`, `assertHoursTransferAllowed` guard requiring TIMEBANK_* `reference_type` + distinct from/to accounts, `HOURS_OPEN_BALANCE` / `HOURS_ARCHIVE_BALANCE` issuer entry types bypass the reference rule for platform-internal opens/archives.
- Hawala-ledger KARMA non-fungible rail: new `karma_event` model (per-member signed-delta event log; `member_id`/`delta`/`reason`/`source_module`/`source_id`/`occurred_at`) + migration. `assertKarmaTransferAllowed` rejects every KARMA-coded ledger-entry attempt with a pointer at the `karma_event` primitive.
- Hawala-ledger top-level dispatcher `assertRailInvariants` — exhaustive per-rail guard via a `never`-typed default so adding a rail to the registry without a guard clause is a compile-time miss. `createTransfer` now calls `assertRailInvariants` instead of the CCR-specific `assertPurchaseContext` (defense in depth: HRS and KARMA paths get their own guards at the ledger layer).
- `dual-rail-selector` hardened to throw `NonCashRailError` on CCR/HRS/KARMA/GIFT — silently routing a closed-loop rail to Stripe-ACH would be a Posture A violation.
- Admin HTTP API surface under `/admin/asset-graph/` (12 endpoints across 11 route files): manifests catalog read, asset-kinds taxonomy read, run-matcher (preview/persist), proposals list/accept/decline, instances list, instance state transitions (publish/pause/reactivate/archive). Consistent error mapping: 400 missing param, 404 unknown slug, 409 invalid transition (with `from`/`action` in body).
- Storefront HTTP API surface under `/store/asset-graph/` (7 endpoints): public manifests catalog, member-side declarations CRUD (filtered/ownership-checked by auth `actor_id`), member-side proposals list/accept/decline (404 on cross-member access — doesn't leak existence).

### Security
- Fail-closed env validators block startup with empty, banned, or under-length secrets in production. Banned set: `supersecret`, `changeme`, `change-me`, `change_me`, `dev-only-secret-change-in-production-32chars`, `test`, `secret`, `password`, anything starting with `CHANGE_ME`.
- `security.yml` workflow adds gitleaks, dependency review, Trivy filesystem + image scanning, CodeQL `security-extended` queries, and CycloneDX SBOM generation per app.
- `dependency-review-action` blocks any PR introducing a dependency with a HIGH+ vulnerability.
