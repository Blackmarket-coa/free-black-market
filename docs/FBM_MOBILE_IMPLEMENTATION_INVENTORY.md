### Additional custom implementations that requiring explicit scope

- **Hermes assistant:** a vendor runtime route can forward chat to an OpenAI-compatible endpoint or n8n. Its tool branch validates `create_vendor`, `create_product` and `delete_product` calls and confirmation fields, then returns the validated call; it does not execute the business mutation. The separate `services/ai-orchestrator/langgraph` directory is prompt/schema guardrail code, not a deployed LangGraph agent. Do not promise autonomous inventory/site/business operation from it.
- **Content-platform connectors:** the service registers generic webhook and RSS adapters by default; TikTok, Instagram, YouTube, Twitch and Blackout adapters are conditional on configuration. These handle account authorization, ownership/metrics/event integration as supported per adapter. They are not product-listing sales-channel adapters or a verified universal cross-posting engine. `podcast` appears in the platform type vocabulary but has no separate registered provider here; RSS can represent a podcast feed.
- **Order subcontracting:** proposal, service-seller acceptance, production/delivery events, dispute and parent-acceptance/settlement references are implemented in the service. This supplies additional B2B building blocks; no complete app journey was verified.
- **Knowledge base:** community contribution submission, moderation, article publication and rejection are implemented. This can support useful learning inside the app; it is distinct from a generic AI knowledge engine.
- **Vendor hype/operations/prediction:** substantial custom models and lifecycle/settlement methods exist. This is a separate gated/sensitive capability, not a reason to treat games, financial positions or payouts as launch-ready. It was indexed but not functionally validated in this task.
- **Notification/feed and chat abstraction:** seller-feed notification provider exists independently of email configuration; Matrix and Blackout chat providers are selected through an adapter. These are separate from native push and should all be accounted for in the app's communication design.

### Reuse implications for the app

Reuse the implemented resource matcher, launch orchestration, Faire synchronization, aid lifecycle/allocation, booking-to-cart link, box scheduler, seller push and parcel tracking. The next work is substantially integration, correction, mobile UI and verification, rather than rebuilding those engines.

A useful first vertical could be: **resource quiz → recommended grower/Plates build → real listing → quote/order or food trade → stock/fulfillment action → seller notification → completed exchange.** The resource matcher can suggest supported projects; actual shared-map publication still needs consented geographic projections and automatic availability updates. Permanent enhanced-tool purchases remain a separate required migration.
